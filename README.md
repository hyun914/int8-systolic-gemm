66# INT8 Systolic GEMM Core

INT8 Output-Stationary systolic array 기반 GEMM 코어를 RTL로 설계하고 검증한 프로젝트이다. 상태별 사이클 식을 세워 RTL 측정값과 비교하고, 배열 크기, 워크로드 shape, 메모리 조건에 따라 성능이 어떻게 달라지는지 분석한다.

> **핵심 질문**: PE를 늘리면 어떤 조건에서 성능이 개선되고, 어떤 조건에서는 개선 폭이 작아지는가?

## 1. 범위

### 고정 사항

- **데이터 형식**: 입력 A/B는 signed INT8, 누산과 출력은 signed INT32
- **Dataflow**: Output Stationary 하나. A는 가로(왼쪽→오른쪽), B는 세로(위→아래)로 이동하고 각 PE가 C[i,j]를 누산기에 유지한다.
- **K 처리**: K 전체를 버퍼에 담는다 (K ≤ `K_MAX`). K 방향 분할은 하지 않는다.
- **실행 순서**: 타일마다 SETUP(누산기 clear) → LOAD → COMPUTE → STORE를 순차 실행한다. 단계 간 중첩(double buffering)은 없다.
- **완료 조건**: 경계 타일도 배열 전체 크기 기준으로 고정 대기한다 (3.1절).
- **Padding**: 배열에 주입하지 않는다. 유효 범위 밖의 행, 열은 valid=0으로 두고, 외부 메모리에서도 유효 원소만 읽는다. 따라서 하드웨어가 센 MAC 수는 정확히 M×N×K여야 한다.
- **배열 크기**: `ROWS`/`COLS` 파라미터로 지정한다. 입력, 누산 비트폭은 고정이다.

### RTL로 검증한 구성

| 구성 | 검증 범위 | 용도 |
|---|---|---|
| 2×2 | 배열 | 연결, 타이밍 손 검증 |
| 2×3, 3×2 | 배열 (2×3은 코어도) | 행/열 인덱스 뒤바뀜 검출 (정방 배열에서는 드러나지 않음) |
| 4×4 | 배열, 코어 | 기준 구성 |
| 8×8 | 배열, 코어 | 배열 크기 비교 |

### 제외

Double buffering, K 분할, AXI, 합성 면적, 전력, SRAM macro 수치.

## 2. 설계 명세

### 2.1 연산

$$C_{M\times N} = A_{M\times K} \times B_{K\times N}, \qquad C[i,j] = \sum_{k=0}^{K-1} A[i,k]\,B[k,j]$$

`gemm_reference(A, B)`는 Python 정수로 계산하므로 INT8 자료형 overflow가 없다. 입력이 INT8 범위를 벗어나거나 누산값이 INT32 범위를 벗어나면 예외를 낸다.

### 2.2 PE (`RTL/PE.v`)

| 포트 | 방향 | 폭 | 설명 |
|---|---|---|---|
| `clk` | in | 1 | |
| `rst_n` | in | 1 | 동기식 active-low reset |
| `clear` | in | 1 | 동기식 active-high clear |
| `a_in`, `b_in` | in | 8 (signed) | 입력 데이터 |
| `a_valid_in`, `b_valid_in` | in | 1 | 입력 valid |
| `a_out`, `b_out` | out | 8 (signed) | 1사이클 지연 전달 데이터 |
| `a_valid_out`, `b_valid_out` | out | 1 | 1사이클 지연 전달 valid |
| `acc_out` | out | 32 (signed) | 누산값 |

- `!rst_n || clear`이면 누산값, 전달 데이터, 전달 valid를 모두 0으로 만든다. reset/clear는 MAC보다 우선한다.
- 정상 동작에서는 A/B와 각 valid를 1사이클 지연해 전달한다.
- `a_valid_in && b_valid_in`일 때만 현재 입력으로 MAC을 수행한다 (16비트 signed 곱 → 32비트 부호 확장 → 누산).
- 한쪽만 유효하면 데이터, valid 전달은 계속하고 누산값은 유지한다.
- PE 내부에는 ready/done 신호가 없다.

### 2.3 배열 (`RTL/systolic_array.v`)

```verilog
module systolic_array #(parameter ROWS = 4, parameter COLS = 4) (...);
```

| 포트 | 방향 | 폭 | 비트 배치 |
|---|---|---|---|
| `clk`, `rst_n`, `clear` | in | 1 | 모든 PE에 같은 사이클에 broadcast |
| `a_in` | in | ROWS×8 | 행 r = `a_in[r*8 +: 8]` (왼쪽 경계) |
| `a_valid_in` | in | ROWS | 행 r = `a_valid_in[r]` |
| `b_in` | in | COLS×8 | 열 c = `b_in[c*8 +: 8]` (위쪽 경계) |
| `b_valid_in` | in | COLS | 열 c = `b_valid_in[c]` |
| `acc_out` | out | ROWS×COLS×32 | PE(r,c) = `acc_out[(r*COLS+c)*32 +: 32]` (row-major) |

- Verilog-2001은 배열 포트를 지원하지 않으므로 1차원으로 펼친다. row-major 배치는 Python `C[i][j]` 순서와 같다.
- 펼친 벡터는 unsigned이다. 부호 연산은 PE 내부에서 처리되며, TB에서 슬라이스를 비교하거나 출력할 때는 `$signed(...)`를 사용한다.
- 오른쪽, 아래쪽 끝 PE의 `a_out`/`b_out`은 외부로 내보내지 않는다.
- 배열은 모든 PE의 acc를 병렬로 내보내고, 코어의 STORE가 이 중 하나씩 골라 메모리에 쓴다 (2.5절).

**내부 연결**

```
a_h[r][c] : PE(r,c)의 a 입력   (c = 0..COLS, [COLS]는 오른쪽 끝 출력)
b_v[r][c] : PE(r,c)의 b 입력   (r = 0..ROWS, [ROWS]는 아래쪽 끝 출력)

a_h[r][0] = a_in 행 r            b_v[0][c] = b_in 열 c
PE(r,c):  a_in ← a_h[r][c],  a_out → a_h[r][c+1]
          b_in ← b_v[r][c],  b_out → b_v[r+1][c]
          valid도 같은 규칙 (av_h, bv_v)
```

연결선 배열을 COLS+1, ROWS+1 크기로 잡아 모든 PE가 "입력 [c], 출력 [c+1]" 규칙을 따르게 한다. 마지막 열, 행의 예외 처리가 없어진다.

PE가 홉마다 1사이클 지연하므로:

```
PE(r,c).a_in(t) = 경계 a_r(t - c)
PE(r,c).b_in(t) = 경계 b_c(t - r)
```

### 2.4 Skew와 2×2 예제

**Skew 규칙**

- 경계 a_r(t) = A[r][t-r], 0 ≤ t-r < K일 때 valid
- 경계 b_c(t) = B[t-c][c], 0 ≤ t-c < K일 때 valid

이때 PE(r,c)는 사이클 t에 A[r][t-r-c]와 B[t-r-c][c]를 받는다. **A[r][k]와 B[k][c]는 PE(r,c)에서 t = k + r + c에 만난다.** 마지막 MAC은 t = K+R+C-3이므로 한 타일의 연산 시간은 **K+R+C-2 사이클**이다.

**예제**: A = [[1,2],[3,4]], B = [[5,6],[7,8]], K = 2 → C = [[19,22],[43,50]]

경계 입력 ("-"는 valid=0)

| t | a_0 | a_1 | b_0 | b_1 |
|---|---|---|---|---|
| 0 | 1 (A00) | - | 5 (B00) | - |
| 1 | 2 (A01) | 3 (A10) | 7 (B10) | 6 (B01) |
| 2 | - | 4 (A11) | - | 8 (B11) |
| 3 | - | - | - | - |

사이클 t에 각 PE가 수행하는 MAC

| t | PE00 | PE01 | PE10 | PE11 |
|---|---|---|---|---|
| 0 | 1×5 (k0) | - | - | - |
| 1 | 2×7 (k1) | 1×6 (k0) | 3×5 (k0) | - |
| 2 | - | 2×8 (k1) | 4×7 (k1) | 3×6 (k0) |
| 3 | - | - | - | 4×8 (k1) |

t의 posedge 직후 acc

| t | PE00 | PE01 | PE10 | PE11 |
|---|---|---|---|---|
| 0 | 5 | 0 | 0 | 0 |
| 1 | 19 | 6 | 15 | 0 |
| 2 | 19 | 22 | 43 | 18 |
| 3 | 19 | 22 | 43 | 50 |

**TB 타이밍 규칙**: negedge에서 경계 입력을 넣고 posedge 후 `#1`에 acc를 확인한다. reset 해제 후 처음 valid 입력이 샘플되는 posedge를 t=0으로 둔다.

### 2.5 GEMM 코어 (`RTL/gemm_core.v`)

```
명령 (M, N, K, base_a, base_b, base_c)
FSM: IDLE -> SETUP -> LOAD -> COMPUTE -> STORE -> 다음 타일이면 SETUP, 마지막이면 DONE

SETUP    배열 clear, load_seq 두 개를 타일 첫 원소로 초기화
LOAD     load_seq(요청) --> 메모리 읽기 요청
         메모리 읽기 응답 --> load_seq(응답)이 정한 bank, 칸에 저장
                              A bank × ROWS, B bank × COLS (bank_buffer)
COMPUTE  edge_feeder × 2 --> bank마다 주소 k = t - i로 동시에 읽기 --> systolic_array
STORE    acc_out에서 유효 원소만 골라 --> 메모리 쓰기 (C)
```

**메모리 배치** (바이트 주소, row-major, 행 사이 빈칸 없음)

- A[i][k] = base_a + i×K + k (INT8)
- B[k][j] = base_b + k×N + j (INT8)
- C[i][j] = base_c + (i×N + j)×4 (INT32, little-endian)

**메모리 인터페이스**: 읽기 요청(`rd_req_valid/ready/addr`), 읽기 응답(`rd_rsp_valid/data`), 쓰기(`wr_valid/ready/addr/data`). 응답은 요청 순서대로 돌아온다고 가정하고, 코어는 응답을 항상 받는다. 읽기는 1바이트/beat, 쓰기는 INT32 1개/beat이다.

**설계 선택**

- **bank 구성**: A는 행마다, B는 열마다 bank를 하나씩 둔다. bank 안 주소는 k이고, bank depth는 K_MAX이다. skew 때문에 행마다 같은 사이클에 읽어야 하는 k가 다르므로, bank를 나눠 bank마다 다른 주소로 동시에 읽는다. bank는 각각 읽기 1개, 쓰기 1개 포트를 가진다.
- **skew 생성**: 레인 i는 COMPUTE 사이클 t에 k = t - i를 읽는다. 지연 레지스터를 쌓지 않고 카운터 하나와 빼기로 skew를 만든다. 다른 구현 방식과의 비교는 7.3절에 있다.
- **padding**: 레인 i ≥ 유효 행(열) 수이면 valid=0으로 둬서 배열에 넣지 않는다. 메모리에서도 유효 원소만 읽는다.
- **로드 순서 두 개**: 요청 쪽과 응답 쪽에 같은 순서 생성기(`load_seq`)를 하나씩 둔다. 응답이 요청 순서대로 오면 응답 쪽 생성기가 돌아온 바이트의 bank와 칸을 알려 주므로, 메모리 지연이 몇 사이클이든 그대로 동작한다.
- **타일 순서**: i(행 타일) 바깥, j(열 타일) 안쪽이다. 타일마다 A와 B를 새로 읽는다 (재사용 정책 P0).
- **TB 메모리 모델**: 항상 ready이고 읽기 응답은 요청 다음 사이클에 온다 (지연 1).

## 3. 사이클 분석

### 3.1 완료 조건

타일마다 배열 전체 크기 기준으로 고정 대기한다. 경계 타일도 같다.

```
COMPUTE 상태 길이 = K + R + C - 2 + L_feed
```

`L_feed`는 bank 읽기 지연이다. bank는 동기식 읽기(주소를 넣은 다음 사이클에 데이터)이므로 `L_feed = 1`이고, COMPUTE는 K+R+C-1 사이클이다. 유효 행, 열까지만 기다리는 조기 종료(K + r_valid + c_valid - 2)는 구현하지 않았다.

### 3.2 상태별 사이클 식

```
T_total = Σ_tiles [ T_setup + T_load(tile) + T_compute + T_store(tile) ] + T_done
```

T_total은 start를 받은 다음 사이클(SETUP)부터 DONE까지 코어가 busy인 사이클 수이다. 이상적 메모리 모델에서 상태별 사이클은 다음과 같다. rv, cv는 타일의 유효 행, 열 수이다.

| 상태 | 사이클 | 내용 |
|---|---|---|
| SETUP | 1 | 누산기 clear, 로드 순서 초기화 |
| LOAD | rv×K + K×cv + 2 | 읽기 요청 1개/사이클, 응답 지연 1, 마지막 응답 확인 1 |
| COMPUTE | K + R + C - 1 | 고정 대기 (L_feed = 1) |
| STORE | rv×cv | 결과 1개/사이클 |
| DONE | 1 | 명령마다 한 번 |

이 식은 RTL 측정값 9개(배열 3가지 × 워크로드 3가지)와 모두 일치한다 (5.4절). 메모리 폭이나 지연이 바뀌면 LOAD와 STORE의 식이 바뀐다.

- 순차 구조이므로 `max(Load, Compute, Store)`를 쓰지 않는다.
- B가 row-major이면 B 타일은 C 바이트 조각 K개로 나뉜다. 한 번에 여러 바이트를 읽는 인터페이스에서는 조각마다 올림이 붙어, 데이터 layout이 load 사이클에 영향을 준다.

### 3.3 지표

| 지표 | 정의 |
|---|---|
| 유효 MAC | M×N×K (padding 제외) |
| 연산 구간 이용률 | 유효 MAC / (R×C×ΣT_compute) |
| 명령 전체 처리율 | 유효 MAC / T_total [MAC/cycle], 정규화 값은 R×C로 나눈다. |
| 외부 전송량 | 외부 메모리 인터페이스를 실제로 통과한 바이트 수 |

### 3.4 Bandwidth: 배열 경계 공급과 외부 전송의 구분

**배열 경계 공급 (온칩 버퍼 → 배열, COMPUTE 상태 동안)**

충분히 채워진 R×C 배열, INT8 입력, PE당 1 MAC/cycle 기준:

| 배열 | 최대 처리율 (MAC/cycle) | 경계 입력 공급 (B/cycle) | AI_edge (MAC/B) |
|---|---|---|---|
| 4×4 | 16 | 8 | 2 |
| 8×8 | 64 | 16 | 4 |
| 16×16 | 256 | 32 | 8 |

배열이 커지면 절대 입력 공급량 R+C는 **증가**하고, MAC당 입력 공급량 (R+C)/(R×C)는 **감소**한다.

**외부 메모리 전송 (LOAD/STORE 상태 동안)**

총량은 버퍼 재사용 정책이 결정한다. 입력만, padding 미전송, Tm = ⌈M/R⌉, Tn = ⌈N/C⌉:

| 정책 | A 바이트 | B 바이트 |
|---|---|---|
| P0: 타일마다 A, B를 새로 로드 (현재 구현) | M×K×Tn | K×N×Tm |
| P1: 같은 타일 행 동안 A 유지 (i 바깥, j 안쪽 루프) | M×K | K×N×Tm |

출력은 두 정책 모두 4×M×N 바이트이다 (K 분할이 없으므로 한 번만 저장). P0에서는 외부 입력 전송 총량이 배열 경계 공급 총량과 같고, 두 값은 버퍼 재사용(P1)부터 갈라진다.

입력 전송량 (P0 / P1, **공식 계산값, RTL 미검증**):

| 워크로드 (M,N,K) | 4×4 | 8×8 | 16×16 |
|---|---|---|---|
| (32,64,64) | 65,536 / 34,816 | 32,768 / 18,432 | 16,384 / 10,240 |
| (1,64,64) | 5,120 / 4,160 | 4,608 / 4,160 | 4,352 / 4,160 |

(1,64,64)는 B 4,096 B가 대부분이고 M=1이라 재사용할 데이터가 없어서, 배열 크기, 정책과 관계없이 전송량이 거의 일정하다. 외부 대역폭이 병목이면 PE를 늘려도 개선 폭이 작아지는 원인이다.

## 5. 검증

### 5.1 PE (`tb/tb_PE.v`)

14개 케이스로 reset과 clear가 MAC보다 우선하는지, 한쪽 valid만 있을 때 누산값을 유지하는지, 음수와 -128, 127 경계값의 signed 곱셈, 실행 중 reset을 확인한다.

### 5.2 2×2 배열 (`tb/tb_array_2x2.v`)

2.4절 표를 매 사이클 손 계산값과 비교한다 (13 step).

- t0~t3 매 사이클 acc 4개가 표와 일치
- 입력이 끝난 뒤 acc 유지
- clear 1사이클 후 acc 전부 0, 다른 행렬(-128/127 포함)로 재실행 시 이전 값이 섞이지 않음

- (-128)(-1) = 128처럼 unsigned 곱셈이면 값이 달라지는 입력, 127×(-2) 같은 음수 곱으로 signed 곱셈과 부호 확장을 확인

### 5.3 배열 랜덤 검증 (`tb/tb_array.v`)

`model/gen_vectors.py`가 만든 무작위 A, B와 정답 C로, 2×2, 2×3, 3×2, 4×4, 8×8 단일 타일(M=R, N=C)과 K ∈ {1, 2, 29, 64}, seed 1~3을 실행한다 (60/60 통과). TB가 skew 규칙대로 경계 입력을 넣는다.

- 매 사이클 모든 PE의 acc가 TB가 계산한 부분합과 일치. 따라서 t = K+R+C-3 posedge 직후 전체가 완료되고, 그 직전 사이클에는 PE(R-1,C-1)에 마지막 곱 하나가 빠져 있음을 확인한다.
- 입력이 끝난 뒤 2사이클 동안 acc 유지, 모든 PE의 최종 acc가 Python 정답 C와 일치

| PE가 valid를 무시하고 항상 MAC | 0/60 | t=1 PE(0,0), 무효 칸의 무작위 값이 누산됨 |
| acc 출력 인덱스를 `r*ROWS+c`로 씀 | 44/60 | 2×3은 시뮬레이션에서, 3×2는 컴파일에서 실패. 정방 배열은 통과 |

- 세 워크로드 결과 전체 일치

| (M,N,K) | 4×4 | 2×3 | 8×8 |
|---|---|---|---|
| (32,64,64) | 77,057 | 137,633 | 37,441 |
| (1,64,64) | 6,369 | 7,131 | 5,329 |
| (7,13,29) | 1,970 | 3,335 | 969 |

모두 3.2절의 상태별 식과 일치한다. 이 메모리 모델에서는 LOAD가 대부분을 차지한다. 예를 들어 4×4의 (32,64,64)는 타일 하나에 602사이클이 걸리는데, 그중 LOAD가 514사이클이다. 그래서 PE를 4배(4×4에서 8×8)로 늘려도 (32,64,64)는 2.06배, (1,64,64)는 1.20배만 빨라진다.

**검증 환경 확인 (버그 주입)**: 4×4와 2×3에서 seed 1로 실행했다.

| 주입한 버그 | 잡힌 검사 | 비고 |
|---|---|---|

| C의 행 간격을 N이 아니라 COLS로 계산 | 중복 쓰기 검사 | 같은 주소를 두 번 씀 |
| B의 행 간격을 N이 아니라 K로 계산 | 메모리 비교 | 잘못된 B를 읽어 결과가 틀림 |

## 6. 결과 표기 원칙

- Python 모델 예측값과 RTL 측정값을 구분해서 표기한다.
- 각 실험에서 고정한 자원과 변경한 자원을 함께 기록한다.
- 파라미터화는 구성별 검증을 대신하지 않는다. RTL 검증 구성은 해당 구성에서 계산 결과, skew, 완료 사이클, 초기화, 경계 처리를 확인한 것만 포함한다.
- 전력 분석, 실제 SRAM macro, 물리 구현을 수행하지 않았으므로 해당 PPA 수치를 주장하지 않는다. behavioral 버퍼를 합성했다면 그 면적은 SRAM macro 기반 면적으로 해석하지 않는다.
- 외부 인터페이스는 단순 ready/valid이며 AMBA AXI 구현이 아니다.
- 이 프로젝트는 Output-Stationary systolic GEMM 코어이며 TPU 전체 구조를 재현한 것이 아니다.

## 7. 개선 항목

### 7.1 카운터와 인덱스 폭을 값의 범위에 맞추기

**현재 상태**: 현재 RTL은 구현을 단순하게 하려고 인덱스와 카운터를 모두 16비트로 통일했다. 예를 들어 `load_seq`의 `lane`은 0~3만 세는데 16비트 레지스터이고, 코어는 필요한 하위 비트만 잘라 쓴다 (`rsp_k[5:0]` 등). 동작은 맞지만 하드웨어로는 낭비다.

**문제**

- 위쪽 비트가 항상 0인 플립플롭이 남는다. "lane이 3을 넘지 않는다"는 사실은 사이클에 따른 값 변화를 따져야 알 수 있어서, 일반적인 합성에서는 이 비트들이 제거되지 않을 수 있다.
- 덧셈기와 비교기가 16비트로 만들어진다 (`lane + 1`, `lane == rows_valid - 1` 등). 비트 폭만큼 면적과 carry 경로가 늘어난다.
- 폭만 보고는 값의 범위, 즉 설계 의도를 알 수 없다.

**필요한 폭**

| 신호 | 현재 | 값의 범위 | 필요한 폭 | 4×4 | 8×8 |
|---|---|---|---|---|---|
| `load_seq.lane`, `gemm_core.rsp_lane` | 16 | 0 ~ max(ROWS, COLS) - 1 | `$clog2(max(ROWS, COLS))` | 2 | 3 |
| `load_seq.k`, `gemm_core.rsp_k` | 16 | 0 ~ K_MAX - 1 | `$clog2(K_MAX)` | 6 | 6 |
| `gemm_core.st_r`, `st_c` | 16 | 0 ~ ROWS - 1, 0 ~ COLS - 1 | `$clog2(ROWS)`, `$clog2(COLS)` | 2 | 3 |
| `rows_valid`, `cols_valid` | 16 | 1 ~ ROWS, 1 ~ COLS | `$clog2(ROWS + 1)`, `$clog2(COLS + 1)` | 3 | 4 |
| `gemm_core.t`, `t_last`, `edge_feeder.t` | 16 | 0 ~ K + ROWS + COLS - 2 | `$clog2(K_MAX + ROWS + COLS - 1)` | 7 | 7 |

**줄이지 않는 것**: 메모리 주소(`addr`, `row_base`, `a_start`, `st_addr` 등)는 주소 공간 AW=16비트가 필요하다. 명령 입력 M, N, K와 타일 위치 `i0`, `j0`는 명령이 정하는 범위라 16비트를 유지한다.

**폭을 줄일 때 주의할 점**

- 번호와 개수는 필요한 폭이 다르다. 번호 0~3은 2비트면 되지만, 개수 1~4는 4 자체를 담아야 해서 3비트가 필요하다 (`rows_valid`).
- `load_seq`는 A(행)와 B(열)에 같은 모듈을 쓰므로, `lane` 폭은 ROWS와 COLS 중 큰 쪽에 맞춘다.
- ROWS=1처럼 `$clog2` 결과가 0이 되는 구성은 폭을 최소 1로 둔다.
- `edge_feeder`의 `k = t - i`는 t < i일 때 값이 감긴다(wrap). 지금은 `t >= i` 조건으로 막고 있으므로, 폭을 줄여도 이 조건은 유지한다.

**효과 확인 방법**: 합성 도구(예: Yosys)로 줄이기 전후의 플립플롭 수와 셀 수를 비교한다. behavioral 버퍼(`bank_buffer`)는 SRAM이 아니므로 제외하고 제어 로직만 비교한다.

### 7.2 메모리 지연 L과 동시에 진행 중인 요청 (outstanding)

**배경**: TB 메모리는 요청 다음 사이클에 응답하는 이상적인 모델이다 (지연 L = 1). 실제 메모리는 칩 안 SRAM이 1~2사이클, 버스를 거친 DRAM은 수십에서 수백 사이클이 걸린다. L은 요청이 받아들여진 사이클부터 응답이 오는 사이클까지의 간격이고, 코어가 아니라 메모리가 정한다.

**현재 코어의 성질**

- 요청을 보낼 때 응답을 기다리지 않는다 (`rd_req_valid = (state == ST_LOAD) && !req_finished`). 그래서 동시에 진행 중인 요청 수가 L만큼 자동으로 늘어나고, 요청 처리율은 L과 관계없이 1개/사이클이다.
- 응답이 들어갈 자리(bank 번호, 칸 번호)가 미리 정해져 있고, 응답 쪽 `load_seq`가 그 자리를 알려 준다. bank 자체가 응답이 저장되는 자리라서, 요청을 많이 겹쳐도 응답을 따로 담아 둘 버퍼가 필요 없다.
- 가정: 응답은 요청 순서대로 오고, 코어는 응답을 항상 받는다 (응답 쪽 ready 없음).

**측정** (4×4, (32,64,64), 타일 128개). TB의 읽기 응답을 L사이클 늦추는 변형으로 측정했다. 측정용 변형은 저장소에 포함하지 않았다.

| 메모리 지연 L | 현재 코어: 전체 사이클 | 현재 코어: 최대 outstanding | 응답을 기다리는 코어 (비교용): 전체 사이클 | 응답을 기다리는 코어: 최대 outstanding |
|---|---|---|---|---|
| 1 | 77,057 | 1 | 142,465 | 1 |
| 4 | 77,441 | 4 | 339,073 | 1 |
| 16 | 78,977 | 16 | 1,125,505 | 1 |

타일당 LOAD 사이클은 현재 코어가 `요청 수 + L + 1`, 응답을 기다리는 코어가 `요청 수 × (L + 1) + 1`이다. 비교용 코어는 `rd_req_valid`에 "진행 중인 요청이 0개일 때만" 조건을 붙인 것이다.

**최대 outstanding을 정하는 숫자**

- 실제로 겹치는 수 = 처리율 × 지연 (Little's law). 요청을 매 사이클 보내면 L이다.
- 최대 처리율을 유지하려면 L × (사이클당 요청 수)만큼 겹칠 수 있어야 한다.
- 현재 코어에는 상한이 없다. 실제 상한은 버스와 메모리가 정한다 (예: AXI의 ID 수와 ID당 깊이, 인터커넥트 큐 깊이). 상한 N이 L보다 작으면 처리율은 N/L 요청/사이클로 떨어진다.

**남은 문제와 후보**

- 타일 단계가 겹치지 않아서 지연을 타일마다 한 번씩 기다린다. 식으로 계산하면 L = 100이면 89,729사이클(+16%), L = 200이면 102,529사이클(+33%)이다 (RTL 미측정). COMPUTE 중에 다음 타일을 미리 요청하면(prefetch, double buffering) 이 지연을 숨길 수 있다.
- 실제 버스를 흉내 내려면 `MAX_OUTSTANDING` 파라미터로 진행 중인 요청 수를 제한하고, 최대 outstanding 카운터로 측정한다. 메모리 모델에는 지연 L을 파라미터로 넣는다.

### 7.3 skew 구현 방식

skew(행 r을 r사이클 늦게 배열에 넣는 것)를 만드는 방법은 두 가지가 있다.

**방법 1: 지연 레지스터.** 넓은 메모리 하나에서 모든 행이 같은 k를 같은 사이클에 읽고, 행 r 앞에 레지스터를 r단 더 둬서 늦춘다 (skew buffer, shift register).

**방법 2: bank별 읽기 주소 (현재 구현).** 행마다 bank를 따로 두고, `edge_feeder`가 레인 i마다 주소 k = t - i를 만든다. 모든 행이 읽기 레지스터 1개만 거치고, 처음부터 한 칸씩 어긋난 원소를 읽어서 skew가 생긴다.

| | 방법 1: 지연 레지스터 | 방법 2: bank별 주소 (현재) |
|---|---|---|
| 버퍼 | 넓은 메모리 1개, 읽기 주소 1개 | 좁은 메모리 R개, 읽기 주소 R개 |
| 추가 레지스터 | R(R-1)/2단 × (데이터 8 + valid 1)비트 | 없음 |
| 추가 조합 회로 | 거의 없음 | 레인마다 뺄셈기, 비교기 |
| 배열이 커질 때 | 레지스터가 R²에 비례해 늘어남 | 주소 회로가 R에 비례해 늘어남 |
| 잘 맞는 구현 | SRAM macro 기반 ASIC. 작은 SRAM을 여러 개 두면 주소 디코더 같은 주변 회로 비중이 커져 면적 효율이 떨어진다 | FPGA (Block RAM이 원래 작은 블록이고 블록마다 주소가 있음), 레지스터로 만든 버퍼 |

방법 1에서 A쪽에 더 필요한 레지스터는 4×4에서 54개, 8×8에서 252개, 16×16에서 1,080개, 128×128에서 73,152개이고, B쪽도 같은 수가 필요하다. PE 하나의 레지스터는 약 50개(a_out 8, b_out 8, valid 2, acc 32)이므로, 양쪽 지연 레지스터는 4×4에서 PE 전체 레지스터의 약 14%, 큰 배열에서 약 18%이다.

**두 방법의 타이밍은 같다.** 행 r의 원소 k가 배열에 도착하는 사이클은 방법 1이 k(읽기) + 1(읽기 레지스터) + r(지연 레지스터), 방법 2가 k + r(읽기) + 1(읽기 레지스터)로 모두 k + r + 1이다. 그래서 방식을 바꿔도 COMPUTE 길이와 전체 사이클이 같고, 같은 테스트로 결과와 사이클을 그대로 비교할 수 있다.

**세 번째 방법**: 소프트웨어(또는 DMA)가 데이터를 메모리에 미리 비스듬하게 배치하면, 넓게 한 번 읽기만 해도 skew가 걸려 있다. 지연 레지스터와 bank별 주소가 모두 필요 없는 대신, 메모리 배치 변환과 padding이 필요하다.

**후보**: `SKEW_MODE` 파라미터로 방법 1과 방법 2를 고를 수 있게 하고, 같은 테스트로 두 방식을 검증한 뒤 합성으로 레지스터 수와 셀 수를 비교한다.
